# Measure patches before calling them improvements

A patch is a change, not a proven improvement. The operator requires individual comparisons, at least eight runs per arm per model for a screen (operator 2026-10-14: four per arm only separates 4/4 from 0/4 at p < 0.05; confirmation sizes come from the experiment-design skill), completion reliability before speed, incremental milestone targets, and a reproducible best-known configuration. This is prospective: the completed twelve-trial contextual-interface cohort remains three runs per arm per model; preserve its original protocol and actual counts. This skill defines evaluation; it does not authorize new runs, runtime edits, resource changes or landing. Use the active worklog and repository gates for authorized implementation. See [story milestones](../pokebench-story-milestones/SKILL.md) for native grading and [game state](../pokebench-game-state/SKILL.md) for qualified observations.

## Check readiness first: is the patch reachable yet?

A patch can only be measured where models actually arrive. The operator's rule (2026-10-14): do not run an experiment until the incumbent can reliably reach the part of the game the patch changes. Before proposing, planning or launching any comparison, decide READY or BLOCKED and say which.

1. **Name the activation milestone:** the earliest native milestone (from `packages/agent/src/milestones.ts`) at or after which the patch first changes what the model sees or does. Ground it in the game, not the feature name. Examples: `counter-talk-v1` first matters at `OLDALE_TOWN` (first Pokémon Center); `ledge-hops-v1` at `ROUTE_101`. A patch active from boot (prompt or observation format everywhere) activates at the first milestone where its text appears.
2. **Measure the current frontier:** count recorded, non-probe, non-human incumbent runs for the model lane and their native milestones. Use the most recent four-plus runs on a build compatible with the incumbent. Human runs, probes, checkpoint starts and replayed gameplay never count toward boot readiness. For a checkpoint design, readiness means the save exists, sits before the activation milestone and loads on the current build.
3. **READY** for a boot comparison only when at least 3 of the last 4 qualifying incumbent runs reach the activation milestone from the planned common start within the planned budget. A checkpoint design is **READY (checkpoint)** when its save passes step 2's checks, whatever the boot frontier; record it as that verdict. Otherwise **BLOCKED**, with the reason "models do not yet reach `<milestone>`": reached/total, the furthest typical milestone, and the run IDs checked.
4. **BLOCKED means:** do not propose, plan or launch a boot comparison. Instead, design a checkpoint comparison from a validated save just before the activation milestone with [experiment design](../pokebench-experiment-design/SKILL.md). The operator's decision (2026-10-15) is to rely on checkpoints heavily. Such a result is conditional on reaching that state, and promotion still needs boot evidence through the winner gate. The patch can still land as a correctness fix behind its switch; landing is not a benefit claim.
5. **Record the verdict** in [`docs/experiments/readiness.md`](../../../docs/experiments/readiness.md): patch, activation milestone, verdict, evidence (counts, run IDs, date). Re-check BLOCKED entries whenever the incumbent's frontier advances past a milestone, and before any experiment plan; never rely on an old READY.

When reporting a newly landed patch, state its readiness verdict in one line.

The experiment queue enforces the boot rule; its `readinessOf` counts boot starts only, so checkpoint designs run as external cohorts (see experiment design). A merged switch is registered as a pending entry in `experiments/`. It moves into the queue only when readiness passes; a BLOCKED entry stays pending with its reason. `just experiment-approve` applies only to queued entries, and an entry is never both pending and queued. See `.claude/skills/experiment-queue/SKILL.md`.

## Register one experimental difference

Before trials, record patch ID/version, hypothesized failure mechanism, target native milestone, maximum budgets, meaningful speed/regression margins, tolerated completion change, downstream check and trial order. Compare the frozen incumbent to a candidate on the same reviewed build with exactly one effective behavioral patch flag differing. Reject unexpected differences, missing dependencies or invalid flag combinations before launch. Record complete effective flags, prompt/interface-document hashes, model/artifact/endpoint and serving configuration, sampling, source/build, ROM/vendor, start state and instrumentation identity. Do not use mutable defaults as provenance.

Keep passive recording, native grading, viewer diagnostics and post-run analysis available in both arms. Prefer deriving diagnostics from existing logs; keep instrumentation version/overhead equal. Warnings, injected context, action restrictions and loop termination are interventions, even when named diagnostics. Make independent interventions independently switchable where feasible. Never ablate isolation, truthful grading, input validation or evidence integrity. If a patch unavoidably combines behavior, declare a composite rather than claim individual attribution.

For the initial reference, inventory current behavior and add retroactive behavioral flags only within authorized implementation scope. Verify that explicit settings reproduce the reference and both branches work. A preset requires a compatible executable; flipping flags cannot recover removed code. Do not pretend the configuration resolver or flags exist before implementing and validating them.

## Run short targets, then extend the frontier

Screen with **eight trials per arm per model**. Confirmation sizes come from `power.py` in [experiment design](../pokebench-experiment-design/SKILL.md), within the operator's GPU-hour budget, and run at a fixed N with one analysis and no early stops (2026-10-15). Use predeclared counterbalanced order (the queue's screens use its Williams order, ABBA for two arms; external cohorts use randomized balanced blocks), identical starting conditions and equal maximum budgets. Terminate after the game-owned target is verified to save time; use an implemented, logged termination path, never silently truncate events or mislabel an operator abort. Retain every launched outcome, stop reason and failure. No gameplay rescue, secret reruns or mid-cohort source/policy changes. Control endpoint contention and serving configuration.

For early testing, bound the target to game creation, accepted name or another immediate native milestone, then extend toward truck exit, clock, starter and gym as supported. Resolve target IDs and predicates from the compared build’s native catalog (`packages/agent/src/milestones.ts`): current IDs include `NEW_GAME_CREATED`, `PLAYER_NAME_CONFIRMED`, `FIRST_TRUCK_EXIT`, `CLOCK_SET` and `STARTER_CHOSEN`. Verify the claimed semantics and source evidence; legacy `PLAYER_NAME_SET` is not interchangeable with accepted name, and starter ownership is distinct from later story handoff. Do not invent a target ID or assume a later branch implements a predicate or termination path. Predeclare the stages. A naming result establishes only that frontier; test downstream behavior before claiming broader improvement. Prefer identical checkpoint starts for any segment question: record the save's provenance and SHA-1, and exclude present-at-start milestones from earned splits. A full-run or promotion claim still needs a common end-to-end start. Additional exploratory or confirmation batches must be labeled, predeclared and authorized, not repeated until a favorable result appears.

## Assess reliability and time together

Report target reached/total, missing or censored outcomes, milestone elapsed times/turns/tokens, spread and relevant diagnostic episodes. Show completion counts beside median/range among completers. Missing splits are not zero. Early termination of a stalled run is a bounded failure, not a faster speedrun. State-changing actions and detector flags are proxies, not proof of useful strategy or wasted time. Separate model failures, observability gaps and infrastructure failures; retain the latter without attributing them to gameplay ability.

Compare downstream splits so an earlier gain cannot hide later degradation. Classify improve, regress or inconclusive using the predeclared criteria; eight runs per arm still do not automatically establish statistical confidence. If completion deteriorates beyond the agreed tolerance, do not promote merely because survivors finish faster. Keep the incumbent on regression or inconclusive evidence. Confirm apparent winners using a fresh predeclared batch before promotion to limit selection bias from repeated hill climbing. Post-run LLM annotations may explain evidence, but never override native grading or measured outcomes.

## Show the human, prior baseline and best run

Every results report and its primary split graphs must include these reference comparisons, or explicitly show why a reference is unavailable:

- The recorded human run, with run ID, native milestone evidence and whether it includes exploration/training. Use acknowledged pauses to show active elapsed time; retain raw wall time and state the timing basis. Never compare pause-adjusted human time to an unlabeled model timing basis.
- The pre-change incumbent/baseline cohort, including all failures and completion denominators. Prefer the previous configuration matching the candidate's common features; identify source, observation, hardware or budget changes. A historical reference is not a same-build randomized control. If the experiment omitted a neither-treatment arm, say so instead of renaming a treatment baseline.
- The best valid recorded agent run for the stated frontier, selected by verified progress first and time to that frontier second. Identify the actual run, model/configuration and selection rule. Exclude probes, human recordings, synthetic/replayed gameplay and invalidated historical milestones. Keep a per-milestone record envelope separate: it may combine runs and must not be drawn or labeled as one achieved run.

Plot individual candidate outcomes or spread with completion counts, a visible human reference and the historical references on the same native milestone/time basis. Use a separate frontier panel when the human reaches much farther; do not hide gym results by graphing only naming/clock. Missing, censored and historically unobserved splits are not zero or proof of failure. Pair graph values with native event sequence, source/config and immutable log hashes. Report absolute seconds and gaps versus each available reference, not only treatment-versus-treatment percentages. A single best run describes a record, not a reliable configuration or promotion.

### Default visual: cumulative milestone lines

Use a single full-progression line chart by default for the comparison UI; The operator explicitly removed the early pacing panel during visual review. Put ordered native milestones on X and cumulative active elapsed minutes on Y (lower is faster). Keep the human line and best valid actual agent-run line visible as reference anchors; overlay the chosen candidate runs/cohort summaries and prior matched baseline with consistent colors. Show individual outcomes or spread and completion counts alongside cohort medians. Keep all required story checkpoints on the full frontier; do not omit recorded intermediate progression to simplify the axis. Add a separate detail view only when requested. The approved example is `runs/reports/dialogue-information-think-fast-n4/reference-v2/reference-splits.png` with its source-qualified data sidecar.

Fit interactive graphs to the available width without horizontal scrolling; let the user select additional runs/configurations while retaining reference anchors. Break lines at missing/unsupported milestones, and distinguish no completion before a cap from an unrecorded event. A best-progress run can be slower at early splits: never replace its points with a cross-run record envelope. Changes in best observed frontier across builds remain historical context, not automatic promotion or proof of a causal improvement. Use a bounded streaming reduction or qualified compact index for large human logs rather than loading the entire raw history just to draw a few splits.

The story frontier axis contains game-advancing events and required progression locations, not optional detours. Follow the story-milestone skill; expose existing house-entry, rival-bedroom and completed rival-introduction splits rather than hiding them inside a home-to-rival gap. Optional lab/aide visits may appear in diagnostic history but must not increase milestone completion counts or the achieved story frontier.

## Track and restore the incumbent

Maintain an append-only promotion/regression ledger and immutable named presets per compatible model/environment lane. Each preset records:

- Complete effective flag vector, explicit OFF values, dependencies and policy/document versions.
- Compatible source/build plus model/artifact, serving/sampling, ROM/vendor, start and measurement protocol.
- Validated milestone frontier, eight-per-arm comparison receipts, confirmation evidence, completion counts and time distributions.
- Parent incumbent, candidate patch ID, decision/reason and rollback reference.

Resolve the preset into the recorded effective configuration and validate it before launch. Expose that identity in run metadata and viewer comparisons. Keep old presets and runs reproducible; do not overwrite the incumbent with the luckiest single run or average one model's regression away using another model's improvement. A diagnostics-only UI change is not a behavioral ablation; qualify it separately for correctness and overhead.


## Report results and expose harness bugs

Every completed or interrupted evaluation produces a report, even when the candidate fails or no recommendation is possible. Lead with improve/regress/inconclusive and a keep/discard/improve recommendation, qualified by model and validated milestone frontier. Distinguish a recommendation from an executed promotion or rollback. A report never promotes a preset automatically; apply any preset/ledger mutation only within the user-authorized implementation and promotion scope. The one sanctioned automatic promotion is the experiment queue's winner gate (operator 2026-10-15): a screening result only nominates finalists, and a finalist becomes the incumbent only by winning predeclared finals from boot (see the experiment-queue skill).

Include:

- Incumbent/candidate preset IDs, compatible build, complete effective flag difference, target/start/budgets, model/environment and actual trial counts against the planned eight per arm.
- Native target completion counts, elapsed-time and turn/token distributions, relevant downstream checks, stop reasons, model errors, infrastructure failures and harness coverage gaps. Show both arms side by side, missing/censored outcomes explicitly and magnitude of change with units. Survivor medians alone cannot establish improvement.
- What worked and what did not, tied to run IDs and event/frame evidence. Separate measured facts from causal hypotheses and optional post-run LLM interpretations. State sample/coverage limitations, unverified behavior and confounding changes plainly.
- Recommendation: KEEP only the supported model/frontier after required confirmation; DISCARD the candidate from the incumbent when valid comparisons show regression or no worthwhile benefit; IMPROVE when an identified weakness suggests a specific revised patch. INCONCLUSIVE retains the incumbent and states the next predeclared test. Discarding a configuration does not delete code, flags or evidence.
- Concrete suggested next patch or diagnostic, proposed target and success/regression criterion. Link reproducible run receipts, comparison report and the append-only decision ledger. Show the incumbent before/after; do not claim it changed until the preset/ledger update actually happened.

When a harness bug is found, say **harness bug** and describe the trigger, incorrect observation/behavior/grading, model impact and supporting evidence. Do not reclassify malformed harness evidence or wrong world state as model inability. Separate an intended correction under test from an unplanned bug that invalidates measurement or comparability. Preserve affected trials and label which conclusions remain valid.

Repair authorized bugs through the repository's tests/review gates, verify the exact failure path and model-visible propagation, then rerun the affected comparison from a common qualified build with eight fresh trials per arm. Freeze the revised protocol before restarting. If a common harness repair changes both arms, remeasure both; do not compare a newly repaired candidate against stale incompatible controls. Before declaring historical evidence irrecoverable, audit both retained screenshots and recorded RAM state using the story-milestone skill; missing milestone rows alone are insufficient. If only analysis/display was wrong and immutable logs or retained screenshots contain sufficient correct evidence, regenerate and validate the report without inventing new gameplay results; rerun when observation, gameplay, timing or grading validity cannot be recovered. Keep original and superseding cohorts separate with the reason for rerun. Never modify active measured source or silently replace failures. A repair may be necessary for correctness even before speed benefit is established; grade those claims separately.

This reporting contract does not grant unlimited reruns: apply the existing user-authorized experiment scope and predeclared stopping/budget rules, and surface repairs that require new scope rather than quietly expanding the cohort.
