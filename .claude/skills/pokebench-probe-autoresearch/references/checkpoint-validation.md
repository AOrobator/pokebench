# Conditional native checkpoint validation

Read when native validation is explicitly authorized and before reserving its compute. A probe-research request alone does not authorize gameplay. A user-approved bounded campaign can preauthorize this transition under recorded evidence gates; do not ask again merely because a qualified phase is next. “Super confident” means the declared evidence gate, not the researcher's subjective certainty.

## Establish a feasible handoff

Require qualified delivery/scoring, a completed replicated action-level benefit comparison and acceptable predeclared controls at the intended scope, plus a frozen feasible native design. Native validation collects gameplay evidence; it need not already have proven the gameplay benefit it is designed to test. Better thinking alone is insufficient to open this gate. A failed or inconclusive action/regression rule does not become a pass because a native test would be interesting.

Use [experiment design](../../pokebench-experiment-design/SKILL.md) for the tier, endpoint, cap and fixed N; [patch evaluation](../../pokebench-patch-evaluation/SKILL.md) for checkpoint readiness and interpretation; [run coordination](../../pokebench-run-coordination/SKILL.md) for every compute window; and [fixed-run launch](../../fixed-run-launch/SKILL.md) for the actual execution and viewer proof. Pass the campaign's explicit power/error and regression contract through this handoff rather than silently adopting weaker generic defaults. Follow the core [power-sizing reference](../../pokebench-decision-probes/references/power-sizing.md). A spending envelope is not an N or a power calculation.

Protect native and confirmation reserves before exploration. Cost restoration/startup, fitting, every planner/executor call, failures and teardown, not only completion latency. If the complete intended comparison cannot fit, preserve the cap and report infeasibility or explicitly declare a narrower claim before sampling. Do not spend the reserve on another attractive prompt revision.

## Qualify the save and agent state

- Pin source run, ROM/vendor/build and save hash. Start strictly before the first decision the intervention affects and prove the target flags are false. Exclude inherited completion from earned progress.
- Restore or deliberately specify the paired agent/harness context: conversation and provider identity, observed dialogue, task memory, planner state, feature state and eligibility. A game save alone does not restore these. Prove the supported continuation path or declare a state-only restart and its narrower estimand; never call that persistence restoration.
- Choose checkpoints covering the actual mechanism. An adjacent “press A” save cannot establish recovery of the whole post-gym scene/travel bottleneck. Related checkpoints/forks remain one source family.
- Prove the candidate reaches the actual native caller, tools and model context with the intended timing and lifecycle. A successful probe-only append is not a live implementation. Any necessary bounded harness change follows its owning worklog, default-OFF feature, tests, review and landing rules; this workflow does not install a general controller.

## Compare native behavior

Freeze incumbent and candidate on the same executable, matched saves/context policy, equal caps and recorded effective settings except the declared intervention. Isolate run directories, servers, ports and leases. Use the approved balanced schedule and preserve all started failures, interruptions and stop reasons. No rescue, arm-dependent retries, invisible action help or mid-batch policy change.

Use a game-owned endpoint within the cap with durable event/state evidence, hash-validated native RAM where available and matched frames. For a Rusturf rescue claim, distinguish map arrival, a taunt, battle initiation, grunt victory and Goods recovery; a model's claim or selected tool is not their native completion. Record who initiated progress: model, harness automatic action or external assistance. Observe suspension/resumption and test retirement separately if a stop-on-target rule ends the run before that behavior can be seen.

Fresh randomized trials from the same inspected checkpoint can support a predeclared conditional success claim. They do not create unseen situations or independent source families. Transfer needs the protected family design; source histories read for research remain development. Keep conditional checkpoint reliability, wider transfer and boot/whole-game benefit distinct.

A supported checkpoint result is not production activation or incumbent/boot promotion. Preserve negative and inconclusive results and return the measured effects, uncertainty, harms, costs and exact claim to the operator. Activation and any broader claim require their own authorized evidence path.
