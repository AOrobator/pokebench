# Coordinate before runs

Operator decision, 2026-10-22: coordinate with everyone affected before starting runs. A free slot or released lease proves availability at one instant, not agreement with another owner's upcoming schedule.

## Before starting or scheduling inference

1. Read the user's current instructions and repository `CLAUDE.md`. Preserve the scope and wording of temporary commands. “Don't touch the GPUs” is a temporary stop instruction unless the user says otherwise; do not rewrite it as a permanent ban. A later request to finish work must be interpreted in context, not silently treated as permission to bypass coordination.
2. Identify the affected endpoints, active runs, scheduler reservations, and owner sessions from local process/lease/runner records. Include owners whose next run could be delayed, not just whoever holds a live lease. Do not query or change hardware against an active instruction not to touch it.
3. Tell Claude through the repository's `just tell-claude` command using its talk-to-Claude skill. Notify the relevant Codex/coordinator sessions through the approved repo messaging workflow. Ask the relay to reach every affected run/scheduler/compute owner if ownership is distributed. Messages are authorized as part of this explicitly invoked coordination workflow; remain within this operational scope.
4. Give a concrete reservation proposal: study/run ID, source/model/build, endpoints, fixed N, estimated and maximum compute time, desired start window, lease behavior, and which existing runs must remain untouched. State separately whether the user authorized the launch and whether other owners have agreed to the compute window.
5. Obtain explicit clearance for that window from affected owners or their designated coordinator. A sent message, mailbox receipt, silence, an idle slot, or an expiring lease is not clearance. If nobody is listening, report the message as queued and keep the launch pending. Continue offline preparation. Do not start a detached worker that can later seize an endpoint before coordination finishes.
6. Once authorization and coordination are established, recheck current reservations and acquire the normal exclusive lease immediately before inference. If ownership, endpoint, window or resource scope changed, coordinate again. Never stop another run, remove its lease, reconfigure its server, or reserve an extra endpoint to make the plan fit.
7. **Launch detached only (operator 2026-11-01).** Gameplay, fixed-run runners, lasting viewers, and model proxies must not be LLM/Cursor-session-owned. Follow `.claude/skills/detached-long-lived-processes/SKILL.md` (`nohup` + logs + pid + `disown`, launching shell exits). Cursor background terminals (`block_until_ms: 0` / `run_in_background`) are forbidden as the process owner — a Cursor restart aborts those as `operator_abort`.

Use the existing decision-probes or fixed-run-launch skill for frozen inputs, fake rehearsal, registration, sampling and proof. This skill does not approve experiments or replace those requirements.

## Run limits belong to the operator

- Record the operator-authorized stopping conditions separately from the shared reservation and from estimates. A reservation grants access to shared resources. A scheduler fallback, inherited supervisor default, or cost estimate is never permission to add or shorten a run limit.
- For a subscription-backed run authorized for a number of turns and a duration, apply those limits. Keep estimated API-equivalent dollars as telemetry only, with no stop threshold unless the operator explicitly sets one. Provider quota and errors can still end inference. Report those separately from local stops.
- If an owner offers a window only with an extra or tighter stop condition, request a window that matches the authorized run. If that is unavailable, tell the operator what changed and get their decision before launch. Do not silently apply the condition or bypass the resource owner's reservation.

## Attached harness capture preflight

The first implemented adapter is the opt-in `just codex-capture` bridge. Read [its local mechanism and commands](../../../docs/explainers/codex-capture.html). It archives one Codex player session, keeps source/summary/action provenance, and binds recorded game turns through tool-call IDs. It rejects unarchived player child-session spawning. It does not attach to or modify an existing running bridge. The preflight and launch authorization below still apply; an empty real-model rehearsal remains inconclusive for readable-summary availability.

Operator decision, 2026-10-25: this section also applies to Codex, Claude Code, Cursor and other external agent harnesses playing through a wrapper, including CPU-only diagnostic play. It governs transcript preservation before attachment; compute coordination above still applies to the resources actually used. It does not authorize launching a run.

Before the first gameplay decision:

1. Bind the actual player session to the run. Record harness name/version, player session and child-session IDs, discovered model identity, actual reasoning effort and summary settings, source commit, bridge identity, native transcript paths, archive destination and capture owner. Distinguish settings of the external player from settings advertised by its compatibility gateway: Astra's gateway reported thinking OFF while its Codex player used medium effort with summaries disabled.
2. Enable the harness/model's supported exposed-thinking or reasoning-summary output before the player turn starts. For Codex, request summaries through the supported session configuration and verify the effective turn context; `summary: none` does not meet this requirement when summaries are supported. Inspect the installed Claude Code/Cursor version's native event/transcript output and supported settings rather than guessing flags or assuming all models expose identical reasoning. Do not add a prompt demanding longer explanations or change reasoning effort merely to obtain a trace: those alter the treatment and need separate authorization.
3. Arrange durable capture of the native transcript/structured stream for the actual session and any player child sessions, starting before play and continuing through tool returns, compaction, reconnects and final shutdown. Copy source data into the run's ignored artifacts, preserving original bytes, ordering, timestamps, record IDs, tool-call IDs, inputs/results, instructions and image references with their underlying artifacts. A path to an ephemeral session file, terminal scrollback, a final summary, or a stream format that drops thinking is insufficient. Retain opaque encrypted/redacted records as opaque; they do not establish readable thinking. Preserve raw source independently from derived readable exports and from context pruning.
4. Bind every bridge request/response to the run ID and game turn, native session, source record IDs or byte ranges, tool-call ID and source/archive hashes. Record which observation/screenshot was delivered, what action was emitted, its tool result, capture status and timing. Do not silently associate a thought with the nearest action by timestamp. Record unresolved mappings and partial coverage explicitly. Session token totals include setup and coordination unless independently attributed; they are not per-game-turn usage.
5. Rehearse the actual adapter and archive path with fake game input, then inspect the durable output. Prove that a nonempty thinking/summary block, ordinary response text, tool arguments/results, a screenshot reference and a second decision survive without truncation; prove source record and game-turn association. If thinking is available upstream but missing downstream, fix capture before attaching. A configuration value alone does not prove delivery. When the provider supports summaries but an ordinary rehearsal emits none, verify the request and capture path and report the inconclusive result; do not label the empty result as provider incapability.
6. If the provider or harness cannot expose readable reasoning, report that limitation before play and obtain an explicit operator exception for a transcript-only attachment. Record the exception and reason in the run receipt. This user's preservation requirement is not an exception. Never substitute a generated retrospective explanation for missing thinking. Missing native transcript capture blocks attachment even if readable reasoning itself is unavailable.

Keep distinct labels and provenance for provider-exposed thinking, provider reasoning summaries, assistant commentary/action explanations, human/coordinator guidance and opaque encrypted/redacted reasoning. A reasoning summary is not raw internal reasoning; opaque records cannot be decrypted through a supported client interface. For possible smaller-model training, retain these distinctions and the delivered observation/action/result chain; do not silently turn summaries or human guidance into model-authored thinking, or assume narrated intent proves native success. This procedure preserves evidence; it neither creates a training dataset nor authorizes training.

During play, verify the archive keeps advancing with the source, report capture gaps or failures promptly and preserve already captured bytes. A capture failure does not grant permission to terminate, restart or modify an active player. Coordinate recovery with the run owner and operator; label the missing interval. After play, seal the archive with final byte counts, hashes, captured range and completeness status. Preserve all native source files and run events; derived exports may omit image bytes for readability only when the original images remain retrievable.

Existing runs are not retroactively capture-qualified. A passive export may recover already exposed material without changing prompts, reasoning settings, bridge behavior or original events, but label its coverage and recovery time. Enabling summaries for a future Codex turn does not establish that they appeared during an already running turn.

Evidence for the Codex distinction: [official reasoning-item documentation](https://developers.openai.com/cookbook/examples/responses_api/reasoning_items) describes opaque encrypted continuation state and separately exposed summaries. Verify the actual installed version and session rather than inferring capability from the documentation alone.

This is an operator workflow requirement, not an implemented universal bridge, background archiver or automatic launch gate. Before using an adapter, its owner must supply and prove the capture path above. Do not claim capture is active merely because this procedure is present.

## During and after the run

- Notify affected owners when sampling actually starts, finishes, fails or is stopped; include the endpoint, counts, and lease disposition. Do not promise a reservation has ended while an owned worker can still send requests.
- On a user stop, stop only the owned worker and release only its verified lease. Preserve partial evidence and the fixed-N analysis boundary. Tell collaborators the user's exact command and the action taken.
- Distinguish a temporary pause, a permanent restriction, a pending coordination request and a cancelled experiment. Correct a misstatement promptly in both user conversation and collaborator messages.
- An interrupted frozen batch is incomplete. Do not silently resume or replace its missing draws; freeze the continuation/replacement plan and coordinate its compute window before launching it.

## Minimum receipt

Record user authorization, recipients, exact reservation proposal, acknowledgments, endpoint/owner snapshot, planned and actual counts, operator-authorized stop conditions, effective preset, gateway, and wrapper or supervisor stop conditions, and release/stop status under the study's ignored `runs/` artifacts. Report messages as **queued** versus **delivered** versus **acknowledged** according to evidence. No acknowledgment means coordination remains pending.
