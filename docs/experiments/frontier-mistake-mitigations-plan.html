Frontier mistake mitigation evaluation plan

October 22, 2026 · Implementation catalogue and preparation status. No experiment, probe, approval or launch is authorized by this page.

1. Mechanisms and priority

The October 22 Frontier mistake ledger has 16 episodes. The candidate bundle includes the treatments below, but bundle membership is not evidence of benefit or activation in a later run. Correctness tests come first. Single-feature comparisons follow only after a checkpoint and context are qualified.

Correctness

Recorded RAM, production wiring, OFF parity and refusal paths

Qualify start

Save hash, native state, context restoration and exposure

Proposed screen

8 fresh trials per arm; fixed N; operator approval required

Confirmation

N, cap and budget from comparable data; currently unresolved

Priority follows severity and prerequisites, not estimated minutes saved. E16 is post-cap evidence; overlapping segment gaps must not be added into a speedup prediction. E10 was faster than the human reference and has no dedicated intervention.

2. Start and native target qualification

Prefer the same validated checkpoint before the decision affected by the switch. The save must exist, have a recorded source and SHA-1, and load reliably on the reviewed source. A native milestone event is not a saved emulator state. A save also does not automatically restore event-derived memory, loss ledgers or prompt history.

Choose one native primary strictly after the loaded state. Present-at-start milestones earn no progress. The early primaries currently present in generic pending entries may be inappropriate for later Route 104, move-learning or leader-rematch exposures; revise and freeze them before approval. Checkpoint readiness requires load and exposure proof. A boot comparison additionally requires at least 3 of the last 4 compatible qualifying incumbent runs reaching activation within the planned common limits. No such counts are supplied here.

3. Arms and effective configuration

For each primary comparison: one frozen reviewed build, one explicit incumbent vector and a candidate differing in exactly one changedFeature. Validate normalized flags, dependencies, prompt/tool hashes, ROM, vendor, model artifact, sampling and start. Hold passive instrumentation and native grading identical.

explorer-family-guidance-v1 represents the family-prompt replacement through one switch; hold both original explorer bits fixed. A manual v1-ON/v2-OFF swap is a separate composite and cannot be mislabeled a single-feature fixed-run comparison. The historical bundle versus control can answer only a composite-bundle question; it cannot attribute benefit to individual treatments.

Existing trigger navigation, move-learning comparison/tool/fingerprint, field-ownership feedback and tool-prompt docs are retained where dependencies hold. Keep story-battle-heal-gate-v1 OFF. Future fixed-point-breaker-v1 bundle ON/control OFF is covered by the six normalized recipe assertions in frontier-mitigations-integration.test.ts; later actual activation still requires a run_start receipt with source SHA, recipe identity and effective flags. Current ON means collapse plus note; positive-supervisor-v1 is not a switch for that note. Keep auto-talk, collapse and note semantics explicit. Individual gym-warning-OFF and rejected-step-OFF ablations are separate optional comparisons, not additional differences hidden inside a primary treatment.

4. Outcomes and decision rule

Correctness: exact native owner/readout/action receipts, source-qualified controls and OFF parity. This can establish interface or execution correctness; it cannot establish better gameplay.

Proposed screening shape: 8 fresh trials per arm per model, fixed N with one final analysis. Primary: native target reached within the equal predeclared cap. The target itself is unresolved until the checkpoint is qualified. Report direction and intervals; a screen is nomination evidence, not promotion or a confirmed claim.

For a later confirm-tier design, freeze one binary native primary and a two-sided exact Fisher decision at 0.05, then power-size the experiment. Secondary measures: time/turns/tokens to primary with failures censored at the cap, furthest native story progress, and mechanism exposure/errors. Do not compute survivor-only medians as overall speed. Keep losses, loops, crashes and model errors in the denominator. Decision annotations never override native grading.

The historical pending-definition limits were registration placeholders, not a costed plan.

Run the repository experiment-design power.py plan with sourced inputs; preserve its exact command/output and any multiple-comparison family. No power command has been run for this catalogue.

6. Order, executors and failure handling

After approval, use randomized balanced blocks and freeze the exact trial order in the approved fixed-run definition for a compatible boot screen, or in the separately qualified checkpoint study plan. Each executor must serve the same discovered model artifact, quantization and context and receive equal arm allocations. Freeze source, start, prompts, flags and grading throughout.

Predeclare native target stop, wall/turn caps, loop/stall policy and every terminal status. Budget, stuck/stalled, crash and model_error are failed primary outcomes. Only demonstrated outside-arm outages can receive predeclared replacements, reported at the end. Preserve operator stops distinctly. No interim looks, early ejections, gameplay rescue or mid-study settings changes.

Size compatible boot screens from the predeclared budget and power analysis, and execute them through operator-approved fixed-run definitions. Checkpoint studies and power-sized confirmation need a separately qualified external driver; this page creates none. Do not set externalCohort merely to imply that a study is active.

7. Threats, omissions and deferred work

Checkpoint results are conditional on reaching the loaded state. Full-run/promotion claims need boot evidence through the operator's winner process. Historical runs have different harness settings and cannot substitute for a randomized same-build control. New treatments may interact; hold the rest of the bundle fixed for attribution.

The M6 audit found the cited productive-training windows covered by existing milestone reset and drought suppression; no new training-cycle treatment is justified by that evidence. This does not claim every possible EXP loop is covered. Keep navigation-recovery-v1, milestone-drought-suppression-v1 and cycle policy explicit and verify the effective source path before study.

Deferred: mandatory rematch gate, automated RUN decisions, route selection, inferred person identities, automatic activation of inferred/unloaded NPCs and any E10-specific patch. None is smuggled into this catalogue. A separately authorized static-npc-template-approach-v1 packet is integrated for qualified stationary non-trainer templates. Its checked approach never activates the target. Approach-only support does not authorize pressing A, automatic conversation/battle, or a claim of current presence. Its card records actual registration metadata; final independent review and exposure-specific evaluation remain pending. Where a packet is narrower than the worklog, preserve that limitation in review and evaluation.
