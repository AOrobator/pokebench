JIT v2 · proposed ten-minute screen

Proposed exploratory screen: stable-prefix instruction delivery versus full standing instructions. One switch: just-in-time-prompt-v2. V1 is OFF in both arms; full tools and execution behavior stay identical.

NOT APPROVED · NOT STARTED. This proposal does not reuse the first experiment’s four GPU-hour authorization. Requires fresh budget approval, reviewed implementation/source pin, startup checkpoint qualification and fresh two-GPU serving verification.

Question and evidence

Does stable instruction delivery reduce cache churn and improve native early-game frontier within ten minutes? V1’s final 24 valid trials had 6.5% smaller logical request input without a latency benefit; scene-change requests showed lower cache reuse. Control won eight of twelve exact frontier comparisons and reached starter handoff in 5/12 versus JIT 1/12. JIT met the rival in 12/12 versus control 10/12, so the direction differs across early and deeper milestones. This is an association confounded by scene, images and history. It is a mechanism hypothesis, not a diagnosed backend defect.

The source-checked full system is 13,939 characters; the v1 overworld system is 10,435. V2 has a fixed 3,308-character core and appends existing scoped guidance. Total history may grow. No claim of a measured benefit.

What is actually being changed

Randomization estimates the total instruction-delivery policy effect: role, placement, recency, scoping, retained volume and prefix stability change together. Cache reuse is a secondary mechanism association, not an identified mediator. Full tool definitions and execution behavior remain identical.

The full unknown fallback is deliberately retained; no specialized Birch-introduction branch is added in this experiment. In v1, 533/1,640 JIT requests used fallback, including 483 Birch-speech requests. A startup fallback anchored to the preserved task remains for the run. Core plus that guide body totals 14,615 characters before its label, compared with control’s 13,939. If an overworld guide also survives, those components total 22,418 characters before labels; additional episodes may coexist. These are text characters, not token estimates or a claim that a particular live request has this volume. A smaller system field is not a success criterion.

Declared analysis contract

Primary outcome: native frontier depth then exact arrival time. The fixed schema still requires a field named primaryMilestone: RIVAL_MET; with primaryOutcome: frontier this is only the secondary reach marker and does not select the ranking endpoint. The fake-data rehearsal checks that frontier ordering remains active. No sixty-second tie rule replaces exact arrival.

Designated mechanism secondary: per-run mean provider uncached input tokens per terminal request, summarized across twelve runs per arm; lower is less recorded input work. Include all terminal responses and separately show successful-response sensitivity for cap cancellations. Cache-read fraction, logical input, TTFT, latency and output are supporting measurements. Record every guide’s anchor, ordinal, scene, source state and exact text. Report retained guide count, total guidance text characters and canonical-history JSON size per request; keep text units distinct from serialization and provider tokens. Report startup, scene changes, eviction reinjection and stable-scene requests separately as descriptive strata. A frontier tie or null result does not erase these measurements.

What this budget can establish

The ten-minute cap carries forward the operator’s early-milestone question, not a claim that ten minutes is enough for rival completion. The primary is explicitly frontier ranking, an operator-authorized departure from the default binary milestone confirmatory template. With 12 per arm this is a nomination screen only. No powered minimum lift was chosen or authorized; a binary-power calculation is a sensitivity check, not power for the frontier endpoint.

The completed comparable v1 cohort reached RIVAL_MET in 10/12 control trials (latest reaching time 517.839s) and 12/12 JIT trials (580.606s). The 600s cap therefore includes the latest observed rival arrival but can censor later-reaching runs. A binary RIVAL_MET sensitivity calculation at 10/12 baseline and 12 per arm has only 1.28% power for +8 percentage points and 3.36% for +16 points (two-sided Fisher, alpha .05); 80% power would require 289 or 52 per arm, respectively. These are not power calculations for the frontier ranking endpoint. Retain four independent persona verdicts before approval. Readiness begins at NEW_GAME_CREATED; startup guidance also needs the pinned checkpoint to load reliably. These qualification items remain visible rather than being inferred from a schema-valid definition.

Deterministic context-pressure rehearsal

A 65-request synthetic alternation between unknown and overworld was projected through the production 20-turn window and pinned provider serializer, with zero HTTP calls or inference. It retained up to 21 guides; the largest serialized payload was 305,654 bytes. Startup carried 11,479 guidance characters including its label, beside the 3,308-character core. The fixture uses synthetic text, placeholder images and five synthetic tool schemas; these are reproducible stress dimensions, not a byte-exact real-game request or provider-token count. This exposes significant context-pressure risk. Before any launch approval, qualify actual chat-template token fit against the 65,536-token lane limit; do not infer token fit from JSON bytes or silently add a new guard.
