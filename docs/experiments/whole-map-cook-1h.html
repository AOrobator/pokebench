6. Order, executors and failures

Six blocks of two pairs each, both GPUs at once. Arms alternate lanes in a seeded balanced order, so each GPU runs each arm 6 times. Before launch both lanes must report the same model file, build, context and slots in /props (today: Qwen3.6-35B-A3B-UD-Q4_K_M, 65536 context, 1 slot). Results are reported per lane too.

Every launched trial counts. A crash or model error counts as not reached. Only an outage outside the arm (llama-server down, an emulator crash with no model call) is re-run at the end and reported. Max 1 hour per run. Launch only via just fixed-run run from an isolated checkout pinned to one main commit; a launch mistake taints the experiment and it restarts clean. The viewer is not restarted during the pin window.

7. What could fool us, and what this cannot tell us

ThreatControl in this design
12 per arm is underpowered for modest gainsPower stated up front; secondaries and mechanism counts reported; no claim of "no effect" from a miss
Many switches togetherCan only nominate the bundle; each switch is confirmed alone before promotion (PB5)
GPU or time-of-day driftEach GPU runs each arm 6 times; pairs run concurrently
Build changes mid-cookOne pinned checkout for all 12 blocks, after every gated fix lands
Control changes before launch (exit-reachability)Both arms use the same control preset at the pin; the baseline cohort predates it
Baseline cohort on older buildsOnly used to choose the primary and the cap, not as a comparison

This cannot say whether any one of the three switches helps, whether the gain holds past one hour, or whether it changes the rival battle or later fights. It also cannot test the stride-length hypothesis on the bundle, since the bundle is not an arm.
