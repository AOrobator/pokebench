Break the shop refusal loop

menu-refusal-recovery-v1 recognizes a battle command repeatedly refused while the game's shop menu is open. It delivers the menu's actual exit control, then bounds further attempts.

Switch OFF

The existing battle refusal guard requires an initialized battle. “No battle is in progress” calls in a shop do not enter that guard. Existing warnings and stopping behavior stay unchanged.

Switch ON

Two no-button battle refusals in the same verified ready shop action menu open one rejection episode. The next decision receives its warning. Six further calls without verified interface recovery stop the run as stuck, including with the generic supervisor enabled.

Qualification and delivery

The current result must reference its coherent native state. Detection requires a started overworld game, no battle, map and position, a ready shop_action_menu with a qualified owner, and a refused battle_action that sent no buttons. HTTP failures, missing states, busy or unsupported UI owners and real button actions do not count.

A verified ready interface change or free field control retires the episode. Missing or transitioning observations leave recovery unproven. Ordinary field-message coverage is independent of the qualified shop UI. Warning, recovery and terminal stop use existing loop_guard events in Activity History and raw inspection; no timeline marks are added.

Scope and status

Recorded-loop replay and the pinned pi request path are tested. These checks establish guard behavior and feedback delivery; model escape rate and benchmark benefit remain unmeasured. Navigation recovery, automatic menu cancellation and changes to existing measured recordings are outside this switch.
