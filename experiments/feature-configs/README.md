# Maintained feature configuration

`current.json` is the sole maintained control/bundle feature owner. `rayquaza-lane.json` is the Rayquaza lane's overlay on it, `{version, id, base, on, off}`: only the lane's differences from `current`, each `on` and `off` entry a `switch: one-line reason` pair, so every control change reaches the lane with no edit here (the operator 2026-11-06). Recipes resolve when read (`resolveFeatureRecipe` in `packages/viewer/src/fixed-design.ts`) into the full recipe shape: the base's romSha1, controlBase, lists and features, with `on` moved to onInBoth with features true and `off` moved to offInBoth with features false. Resolution fails naming the switch if the base does not know it or it is both on and off, and fails if the base is itself an overlay. The recipe and definition hashes cover the resolved recipe, so a control change shows in the hash of every lane definition that inherits it; reasons are not part of the resolved recipe. Each run records the full resolved switch list and its hash in run_start (`evaluation.features`, `evaluation.features_sha256`), and `fixed-run check` on a lane definition prints the switches that changed since the lane's last recorded run. A launched experiment keeps its recipe: `fixed-run run` stores the resolved recipe in `runs/experiments/<id>/resolved-recipe.json`, and once the ledger has a launch, run and rerun read that file (or derive it from the experiment's presets, whose bytes must match the launch) and presets are not rewritten; `check`, `analyze` (which compares no features) and fresh experiments resolve live. The lane has no plain preset; it runs through its fixed definitions. Add new feature defaults and arm activation here, not to protocol copies. `features` is the shared base; `switches` turns a flag OFF in control and ON in bundle; `onInBoth` and `offInBoth` record explicit common settings. Keep every both-arm promotion in the shared base too.

The shared baseline is the current two-hour Qwen control (including full-map navigation), retaining explicit both-arm promotions from both former donors, including original-speed-pacing-v1, named-warp-destinations-v1 and exit-labels-v2. The NPC switch is OFF by default/control and ON in bundle. Global harness defaults are separate.

`bundle-v-control`, `bundle-v-control-2h`, `glm53-flash-4h` and `hyperqwen-control-3h` retain their schedules, models, starts and budgets and reference `featureRecipe: current`. Source loading uses `readFixedDefinition(root,id)`; pure `parseFixedDefinition` still accepts complete frozen/historical definitions without reading current configuration. When parsing a reference explicitly, pass a recipe-text resolver. Each launch records a definition hash over the source and config bytes in its ledger; generated presets/definitions are complete snapshots. Exploratory launches save the resolved definition and feature-config digest in their existing feature-recipe receipt.

Future launchers use the protocol reference automatically; the older `--feature-recipe` option still supports historical full-definition donors. Existing running controllers, environment, leases, run pins, artifacts and schedules are not changed by this migration. Updating tracked source affects only future launchers built from the landed pin.

Read-only historical analysis explicitly permits `readFixedDefinition(root,id,true)` to fall back to `experiments/archive/fixed/`; launch and plan paths do not. The viewer's existing provenance index reads archived titles after current titles so recorded runs remain discoverable.
